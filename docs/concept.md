# 配信対戦管理ツール 検討資料（v0.1）

## 1. 目的

YouTube でゲーム配信中に行う「視聴者参加型ルームマッチ」の進行を自動化する。

- 参加表明：視聴者が YouTube チャットに `!参加` と書く
- 対戦順管理：ツールが待機列・対戦カードを自動で組む
- 告知：次の対戦をツール画面／配信オーバーレイ／YouTube チャットに出す
- 結果記録：配信者がワンクリックで勝敗入力 → 次の対戦へ自動で進む
- （将来）配信画面をキャプチャして勝敗を自動判定

## 2. 全体構成案

```
┌──────────────── Windows アプリ（1個の exe / スタートメニュー登録）────────────────┐
│                                                                                │
│  Electron (内部で Node.js が動く)                                                │
│   ├─ メインプロセス                                                             │
│   │   ├─ YouTube 連携（チャット取得 / Bot 投稿）                                 │
│   │   ├─ 対戦進行エンジン（待機列・マッチング・戦績）                             │
│   │   ├─ データ保存（SQLite or JSON ファイル）                                   │
│   │   └─ ローカル HTTP/WebSocket サーバ (localhost:17xx)                          │
│   │         └─ /overlay  … OBS の「ブラウザソース」で読み込む配信用画面           │
│   └─ 管理画面ウィンドウ（Web UI）                                               │
└────────────────────────────────────────────────────────────────────────────────┘
        ▲ チャット取得 / 投稿                     ▲ ブラウザソース
   YouTube Live Chat API                          OBS Studio
```

### パッケージング候補

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| **Electron（推奨）** | Node.js + Chromium を同梱した exe | 要望の「exe を叩くと中で Node が動く」そのもの。インストーラ（NSIS）でスタートメニュー登録も簡単 | サイズが 100MB 前後 |
| Tauri | Rust + OS の WebView | 軽い（10MB 程度） | バックエンドが Rust。Node の YouTube 系ライブラリを使うには sidecar 構成が必要 |
| Node 単体 exe（SEA）+ 既定ブラウザ起動 | exe がサーバを起動しブラウザを開く | 最も単純 | 「アプリ感」が薄い。終了操作が分かりにくい |

→ Electron で進め、OBS 用オーバーレイだけ内蔵 HTTP サーバから配信する形が素直。

## 3. 機能一覧（MVP → 将来）

### MVP
1. **参加受付**：チャットコマンド `!参加 <ゲーム内ID>`（ID 必須） / `!辞退` / `!順番`（自分の順番を返信） / `!ID <新ID>`（ID 修正）
2. **待機列管理**：自動追加、ドラッグで並べ替え、一時保留（離席）、除外
3. **対戦形式**（後述）の選択
4. **対戦進行**：現在の対戦・次の対戦・その次を常時表示。勝者ボタンで結果記録→自動で次へ
5. **告知**：次の対戦を YouTube チャットへ Bot 投稿（テンプレート編集可）
6. **OBS オーバーレイ**：現在の対戦／待機列／参加方法を配信画面に表示
7. **戦績**：勝敗・連勝数・対戦履歴。配信ごとにセッション保存、CSV 出力

### 将来
- 画面キャプチャによる勝敗自動判定（OBS WebSocket でスクショ取得 → 画像マッチング/OCR）
- メンバー優先枠、1人あたり対戦回数上限
- 複数配信をまたいだ通算ランキング

## 4. 対戦形式の候補

| 形式 | 動き | 向いている場面 |
|---|---|---|
| 勝ち抜き（勝ち残り） | 勝者が残り、敗者は列の最後尾へ。N 連勝で強制交代 | 配信者 vs 視聴者、大人数 |
| ローテーション | 列の先頭2人が対戦 → 2人とも最後尾へ | 全員に均等に出番を回したい |
| 配信者チャレンジ | 常に「配信者 vs 列の先頭」 | 配信者が相手をする企画 |
| 総当たり | 参加確定メンバーで全組合せ | 少人数・締切あり |
| トーナメント | 締切後にブラケット生成 | イベント回 |
| 協力プレイ（2026-09-23 追加） | 配信者のパーティーにゲストが入り、ボス撃破/全滅で交代。ゲスト死亡はその人だけ交代 | エルデンリング、ダークソウル、地球防衛軍 |

## 5. YouTube 連携の論点（要検証）

- **チャット取得**：YouTube Data API v3 `liveChatMessages.list` をポーリング。
  1回 約5ユニット、既定クォータ 10,000/日 のため、5秒間隔×2時間 ≒ 7,200 ユニットで余裕が少ない。
  → 新しいストリーミング取得（`liveChatMessages.streamList`）が使えるか、クォータ消費と合わせて検証する。
  → 非公式ライブラリ（チャット画面の内部 API を読む方式）はクォータ不要だが規約・安定性のリスクあり。
- **Bot 投稿**：`liveChatMessages.insert`（約50ユニット/回）。OAuth 認証が必要。
  配信者本人アカウントで投稿するか、Bot 用サブアカウント（モデレーター付与）で投稿するかを決める。
- **Google Cloud プロジェクト**の作成と OAuth クライアント ID 発行が初回のみ必要。
- 投稿しすぎ防止：告知は「対戦確定時のみ」「最低間隔 N 秒」などのレート制御を入れる。

## 6. データモデル（案）

- `Session`（配信回）：id, 配信URL, 開始日時, 形式, 設定
- `Player`：YouTubeチャンネルID, 表示名, ゲーム内ID, 参加時刻, 状態(待機/対戦中/保留/終了), メンバーか
- `Match`：id, 回戦番号, player1, player2, 勝者, 開始/終了時刻, 判定方法(手動/自動)
- `ChatLog`：受信コメント、コマンド解釈結果、Bot投稿履歴

## 7. 決めたいこと（オーナー確認事項）

1. 対象ゲーム名と、1試合の人数 → **1対1 が基本、2対2 のゲームもある（2026-09-23）**。2対2 は列の順に自動でチームを組む
2. 配信者自身が対戦に入るか → **場合による（2026-09-23）**。「参加しない / 毎試合出る / 列に並ぶ / 勝ち抜きの王者役」を配信中に切り替え可能にした
3. 主に使いたい対戦形式
4. ~~参加者にゲーム内 ID（フレンドコード等）の入力を求めるか~~ → **求める（2026-09-23 決定）**
   - `!参加 <ゲーム内ID>` 必須。ID なしの場合は Bot が書き方を返信。2回目以降の参加は登録済み ID を再利用
   - `!ID <新ID>` で修正可能。他の参加者と重複する ID は拒否
5. Bot 投稿アカウント（本人 or サブ）
6. OBS を使っているか（オーバーレイ・将来の自動判定の前提）
